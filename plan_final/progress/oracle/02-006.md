- 2026-05-14 architecture decision: capture system-audio output via WASAPI loopback from the default render endpoint. Chocolate Doom plays its SDL_mixer output through that endpoint, and WASAPI is the only Windows path that captures another process's audio without requiring per-host Stereo Mix configuration. Raw `bun:ffi` COM vtable dispatch (CoInitializeEx + CoCreateInstance via `ole32.dll` → IMMDeviceEnumerator → IMMDevice → IAudioClient with `AUDCLNT_STREAMFLAGS_LOOPBACK` → IAudioCaptureClient) is the chosen approach because there is no `IAudioClient` binding in the local `@bun-win32/*` packages. `read.u64` reads vtable pointers; `CFunction` wraps each method pointer; bigint COM object pointers feed back as the `this` argument.
- 2026-05-14 window design: define three high-level phases that compose every fixture window — `clean-launch` (≈3000 ms after SDL window appears, covers the title intro + first menu sfx region), `menu-navigation` (≈2000 ms while the Esc→Enter→Enter→Enter menu route is replayed via PostMessageW), `e1m1-start` (≈4000 ms immediately after the final Enter lands the player on E1M1). Three category hashes per phase: `sfx`, `music-event`, `mixed`. WASAPI captures the post-mix output stream, so all three categories on a given phase hash the same captured PCM bytes — but every triple is recorded so downstream gates can compare per-window-category triples. The mixed hash is authoritative for byte-perfect audio parity at the WASAPI capture point.
